Set up this project. Mechanics: `aaxis-oro setup --help`. Idempotent; re-run any time. Never commit in the project; print git commands for the user instead. Keep output terse.

1. Run `aaxis-oro setup status`. It prints one line per area (`foundation`, `claude-md`, `project-md`, `rules` (triage pending until applied), `config`, `oro-ai-gitignore`, `oro-version`, `atlas`, `env`, `memory`) and exits 2 when something is left to do; all done: say so and stop.
2. Foundation (official `orocommerce-foundation:setup`, never reimplemented). Skip when `foundation` is `done`.
   - If `claude-md` is `handwritten`, first run `aaxis-oro setup rules` (snapshots the original, writes the rule table), then triage (step 3) BEFORE the foundation run, because the foundation rebuilds CLAUDE.md with `--force`.
   - Then invoke the `orocommerce-foundation:setup` skill (services project, version from `oro-version`; `--force` only for a handwritten CLAUDE.md). Do not hand-write CLAUDE_base.md.
3. Rule triage (only for a handwritten CLAUDE.md): read `.oro-ai/setup/rules.md`, classify each rule: `keep` in CLAUDE.md (written inside the `<!-- claude-notes -->` sentinels, the only text the foundation's `--force` rebuild preserves), `move` to CLAUDE_project.md, or `drop` because `aaxis-oro:solutions` or the atlas/env/spec skills already cover it (check before claiming). Rules that are about the plugin's own stack (atlas-first, interceptor, e2e) are drops; project facts and team conventions are moves. Present ONE table (id | rule | action | reason) with AskUserQuestion; no writes before the answer. After the foundation run, write the plan `{"items":[{"id":1,"action":"keep|move|drop"}]}` to the scratchpad and run `aaxis-oro setup apply-rules --plan <file>`.
4. Run `aaxis-oro setup sync` (after the foundation step, so its Storefront themes section exists): creates CLAUDE_project.md when missing, syncs the `process-rules`, `review-rules` and `plan-rules` blocks between their markers (ticket process that overrides any command's fast path; extension design must consult and cite `aaxis-oro:solutions` + Oro docs; planner Step 5b dispatches `aaxis-oro:architect-gate` as a 4th plan review), creates `.oro-ai/config.json` and `.oro-ai/.gitignore`. When files are tracked under `.oro-ai` it does NOT create the `.gitignore`: relay the printed `git rm -r --cached` plan, including its warning that teammates lose the files on pull, and tell the user to run it, then `aaxis-oro setup sync` again. Mention any rule in CLAUDE.md that says `.oro-ai` is fully tracked: it contradicts the standard and belongs in the triage table as a rewrite.
5. Print, do not run: the atlas build command from `atlas` (build is slow; the user decides), `aaxis-oro env setup --project <root>` when `env` is missing (hand off; it asks its own questions), `/aaxis-oro:notes-migrate` when `memory` reports unmigrated memories.
6. Finish with `aaxis-oro setup status` and report the remaining TODO lines in at most 10 lines.
